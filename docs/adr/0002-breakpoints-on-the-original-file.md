# 0002 断点打在原始 .clx 文件上，不生成源码副本

日期：2026-11-26
状态：已采纳

## 背景

1.0 及更早版本的调试器会在工作区里生成一个 `debug_temp.clx`，把模拟器返回的源码写进去，然后让 VS Code 在这个副本上显示断点和当前执行位置。

这个做法带来三个问题：

1. **两份行号语义。** 用户在原文件上看到的行号、副本里的行号、协议里的行号三者需要互相换算。历史上已经因此出过一次线上的断点偏移 bug（`63afed4`）。
2. **副本是多余的。** 模拟器从不读那个文件 —— 它只认内部名为 `__lua__` 的缓冲区。副本存在的唯一理由是"让 VS Code 有个文件可以显示断点"。
3. **每次连接泄漏一个监听器。** 只读守卫 `workspace.onWillSaveTextDocument` 注册在应答回调里，从不 dispose。

## 决定

**不生成源码副本。断点、当前行、栈帧全部落在用户原始的 `.clx` 文件上。**

关键事实（源码级确认，见 `msl_naturexd` 仓库的 `c/coloX/src/coloX_core.c`）：

```c
coloX_lua_DoString(vm, cart->_luastr, cart->_luastrlen, &err, "__lua__");
```

卡带的 Lua 以固定名字 `__lua__` 注册进模拟器的源码表。所以 `b __lua__:<行号>` 寻址的是那个缓冲区，**磁盘上有没有对应文件与协议无关**。

行号换算由 `src/debug/lineMapping.ts` 负责：以 `src __lua__` 返回的实际内容做校准，而不是假设偏移量。

## 后果

**必须遵守的约束：行号映射建立不起来时拒绝启动调试，不要回退到生成副本。**

错位的断点比没有断点更难排查 —— 用户会以为逻辑有问题。回退到副本会重新引入本 ADR 要消灭的两份行号语义。模拟器报错或源码对不上时，弹一次明确的失败，不给"看起来能用但行号是错的"状态。

其他后果：

- 空白行上的断点由模拟器自己拒绝（应答 `there is no code at …`），插件把它映射成 DAP 的 `verified: false`。**不做本地"这行可执行吗"的预判**，也不自动吸附到下一行 —— 那个判断和 Lua 语法绑定，必然和模拟器不一致。
- `#include` 会把被包含文件的字节直接拼进缓冲区，所以纯行数模型必然不准。校准以内容为准，`#include` 的行数解析只做交叉校验；两者不一致时失败而不是静默错位。
- 调试结束后不再需要删文件、关标签、摘监听器，`disconnectRequest` 因此简化。

## 已知的协议缺陷

`i local` 命令在模拟器侧有帧偏移 bug（`coloX_dbg.cpp` 里内嵌 Lua helper 硬编码了 `debug.getlocal(frame + 2, …)` 的 `+ 2`），总是报卡带顶层 chunk 而不是停下那一帧，因此拿不到真正的局部变量。

同一帧上 `p <名字>` 能正确解析局部变量和 upvalue。所以 Variables 面板的 Locals 作用域在这种构建上会明确提示改用调试控制台的 `p`，而不是显示一个骗人的空列表。上游修好后自动生效。
